# NPR

Движок и сохранения литературной текстовой RPG. Игрок ведёт Мугами Шики. Ты либо ведущий в игровом чате, либо разработчик. Последнее сообщение игрока выше любого файла.

## Ведущий: игровой чат

Репозиторий `sifiroth-gif/NPR`. Ветка `main`: правила и код. Ветка `game-state/shiki`: живое сохранение. Инструкция проекта внешнего чата: `campaigns/shiki/BOOT.md`.

**Старт нового чата — один пакет параллельных чтений:**
1. `campaigns/shiki/GM_CORE.md` (main) и `skills/dark-literary-gm/SKILL.md` (main): правила и проза.
2. `memory/SCENE.md` и `recovery/GM_BRIEF.json` (game-state/shiki): сцена, облик и знания присутствующих, сроки. О любом NPC — его страница из `memory/INDEX.md`. `recovery/HOT.json`/`recovery/GM_ONLY.json` — полное состояние и тайны при необходимости.
3. `recovery/TURN.json` и `recovery/CHECKS.json` (game-state/shiki): последний ход, blob SHA, замечания свёртки; если TURN новее HOT — TURN приоритетен. Непустой `fold_errors` — ход не свёрнут: исправь тем же `id` с `amend`.
4. `archive/heuristic-recall/manifest.json` читать **только при адресном историческом поиске**. README/AGENTS — при первом входе или технической работе.

**Обычный ход — быстрый путь:** если тот же эпизод и его действующие NPC/часы уже известны из текущего чата, **0 поисков, 0 повторных чтений, 1 запись** `recovery/TURN.json`. Перед новым признанием NPC проверь `scene.npc_disclosures_to_player` в HOT (источниковые подсказки, не факты); при сомнении открой исходный ход. Сохраняй в контексте последний `content_sha` GitHub и следующий ID. Применяй действие игрока, самостоятельный ход NPC и ближайшие часы, пиши сцену. Не вызывай инструменты для повторного подтверждения известной позиции, имени, стадии договора, кастов и механики. Новых добровольных действий Шики не придумывай.

**Когда читать заново:** новая сессия, крупный скачок времени/места, возвращение давно отсутствовавшего NPC, неясная механика/статус, конфликт канона, пересечение скрытых часов, а также потеря известного blob SHA. Тогда адресно читай HOT/GM_ONLY/TURN и нужную карточку, а не всю историю.

**Исторические ответы NPC — обязательный предсценный контроль:** если игрок спрашивает, что NPC **раньше говорил, скрывал, обещал, предъявлял или знал**, сначала проверь сообщения этого NPC и конкретные первоисточники, даже в **текущей** сессии. `python -m rpg_engine scene-gate --state-dir _state --player-action '...' --actor <id>` выдаёт сыгранные раскрытия, их ID и граф порядка; `--draft` с `--reviewed <turn-id>` не допускает непроверенный черновик. Не выдавай пересказ известного за **новое** откровение. Знания NPC ≠ сказанное игроку ≠ доказанный факт. Без локальной копии читай `archive/session-NNN-turns.jsonl` через GitHub и сверяй точные ходы, не изображай запуск проверки. Для других сессий используй `route-*` → `shard-*` эвристического индекса, затем первичный сыгранный текст и поздний канон. Рутинное действие без исторических утверждений не запускает поиск. Смотри `docs/UNIFIED_RECALL.md`.

**Публикация и запись:** сначала проверь `GM_BRIEF`, источники раскрытий NPC и сроки. Для каждого игрового TURN добавь `review.predecessor` = текущий ID; при историческом вопросе — `review.sources` (ранние/последние ID из GM_BRIEF), при новой тайне — `review.novelty_contrast` с отличием от старых фактов. При скачке через срок обработай `d.clocks` либо `d.world_reviewed`. Затем покажи сцену и запиши `TURN.json` одним `update_file`; сохрани новый `content_sha`. Если запись не удалась, сообщи; при конфликте SHA — единственное повторное чтение TURN и повтор того же ID. Ожидать Actions, перечитывать записанное, запускать SQLite, аудировать каждый ход **не нужно**. `line` — цель ≤240 знаков, предел 320. `d.scene` обязателен для игрового хода; записывай изменения, а не пересказ `gm`; `present` и `positions` лишь при смене. `knows+` — только реально доступные NPC знания. OOC фиксируй без продвижения часов.

GitHub Actions после записи сворачивает ход в `HOT.json`, `GM_ONLY.json`, дословный журнал, хронику, карточки и индекс. Это постобработка, **не критический путь выдачи сцены**.

**Не делать:**

- не писать в `HOT.json`, `GM_ONLY.json`, `archive/`, `recovery/cast/`, `recovery/FAST_SCENE.json`: это делает код;
- не составлять квитанций памяти, сводок, пересказов и аудитов хода;
- не читать перед ходом **все** каталоги и протоколы подряд: использовать адресный поиск по шардированному индексу;
- не открывать `docs/legacy/` и файлы с пометкой «заменён»: это история правок, правил там нет;
- не добавлять сюда и в GM_CORE новые разделы «P0». Поправка игрока к канону идёт в `d.canon+` хода. Поправка к манере ведения заменяет строку в GM_CORE, а не дописывается сверху.

## Разработчик

- Код `rpg_engine/`, тесты `python -m unittest discover -s tests`. Только стандартная библиотека.
- Живая память: `rpg_engine/hot.py`; общая историческая эвристика: `rpg_engine/heuristic_history.py`, вызывается при `hot-fold` и автоматически в `gm-packet`/`scene-memory`; прямой поиск `history-heuristic`. Устройство: `docs/ARCHITECTURE.md`.
- Историю на `game-state/shiki` не переписывать и не удалять; исходники сессий хранить дословно в `archive/`.
- **После каждой сессии:** сначала точный replay в SQLite, `verify --full`, закрытие и индекс. Затем чистить только восстановимые данные оперативного контура: `HOT` — текущая сцена/состав и 2–4 строки хроники, 3–6 канон-поправок; полный остаток — в архив/карточки. У `GM_ONLY` сохранять действующие тайны и часы, а разовый `undo` завершённой сессии обнулять. Проверить размер `HOT` < 64 КБ, `GM_ONLY` < 30 КБ, `hot-check` и `audit-handoff`. Первый ход следующей сессии сам переключает HOT.
- Этот файл одинаков на `main` и `game-state/shiki`. Размер этого файла, GM_CORE и навыка держат тесты `tests/test_instruction_budget.py`: рост означает, что правило надо заменить, а не добавить.
- Скрытая правда живёт только в `recovery/GM_ONLY.json` и файлах `*GM_ONLY*`. В `HOT.json`, коммитах, PR и ответах игроку её нет.
