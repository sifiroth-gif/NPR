# Движок текстовой RPG

Движок для кампании, которую ведёт мастер в чате. Сеттинг, правила мира, персонажи и начальные условия задаются при создании кампании. Ядро переносит из исходного проекта модель фактов и знаний, журнал с полнотекстовым поиском и устойчивую случайность. Мастер отвечает за сюжет, мотивы и интерпретацию действий. Движок хранит состояние, применяет последствия и проверяет порядок событий.

**Единый оперативный контур сцены:** [память, граф, знания NPC, автономные часы и проверка черновиков](docs/LIVE_SCENE_PIPELINE.md). В приватной ветке создаётся `recovery/GM_BRIEF.json`, а `recovery/GATE_POLICY.json` включает проверку источников каждого нового игрового хода. Для глубокого поиска по всей истории: `python -m rpg_engine live-preflight --state-dir STATE --action "вопрос"`.

**Живая игра в чате** идёт без SQLite: ведущий читает `recovery/HOT.json` и пишет один `recovery/TURN.json` на ход, остальное сворачивает код. Порядок — в [AGENTS.md](AGENTS.md), устройство — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Для закрытых сессий, поиска по журналу и восстановления начните с `python -m rpg_engine --db campaign.sqlite gm-packet`. [Руководство длительной кампании](docs/LONG_CAMPAIGN.md) описывает подготовку сцены, память, поиск, автономные дела и межсессионный переход. Новый сеттинг создаётся командой `new-setting <путь>`. Флаг `--portable` экспортирует универсальный движок с пустым шаблоном.

## Новая кампания

Нужен Python 3.10+ со SQLite FTS5. Команды выполняются из корня репозитория. Git нужен для синхронизации с удалённой веткой.

```bash
python -m rpg_engine template > campaign.json
# Заполнить название, персонажа игрока, место и начальное игровое время.
python -m rpg_engine init campaign.json
python -m rpg_engine context --audience gm
```

`init` создаёт `campaign.sqlite` с первой сессией и ревизией 0. Другой путь указывается до команды, например `python -m rpg_engine --db games/my-game.sqlite context`. Идентификаторы состоят из латинских букв, цифр и знаков `_.:-`. Имена и тексты поддерживают Unicode. Игровые даты используют формат `ГГГГ-ММ-ДДTчч:мм:сс` без часового пояса.

| Поле конфигурации | Назначение |
| --- | --- |
| `id`, `title` | Идентификатор и название кампании |
| `player` | Объект с полями `id` и `name` |
| `start_at`, `location` | Начальные время и место сцены |
| `rules` | Доступные игроку правила в JSON. Мастер применяет их при разрешении действий |
| `npcs` | Список объектов с `id`, `name` и опциональным `profile`. Профиль может содержать мотивы, цели, связи и возможности NPC |
| `operations` | Начальные факты, знания и открытые процессы |

## Один ход

Мастер читает текущую сцену через `context --audience gm`, а сведения о конкретном NPC через `world --audience gm --subject <id>`. Если действие требует случайной проверки, мастер привязывает бросок к идентификаторам хода и проверки. Результат сохраняется до возврата команды. Повтор с теми же параметрами возвращает те же кости и итог.

```bash
python -m rpg_engine roll --turn t001 --revision 0 --check listen --sides 20 --purpose "Услышать шаги за дверью"
```

После разрешения действий мастер составляет пакет. `player_input` сохраняет исходный ввод игрока. Для вступления или самостоятельного хода мира подходит пустая строка. `text` содержит полный ответ, который увидит игрок.

```json
{
  "id": "t001",
  "expected_revision": 0,
  "at": "0001-01-01T09:00:00",
  "location": "Стартовая локация",
  "player_input": "",
  "text": "За дверью послышались шаги.",
  "events": []
}
```

1. `python -m rpg_engine prepare turn.json` проверяет пакет и сохраняет ответ с `draft_sha`. Мастер показывает игроку ровно текст из квитанции.
2. Когда публикация ответа подтверждена, `python -m rpg_engine confirm --turn t001 --draft-sha <sha>` одновременно фиксирует реплики, мировые последствия и новую ревизию. Повтор с той же квитанцией безопасен.
3. Если чат оборвался, `context --audience gm` восстанавливает сыгранную сцену и отдельно показывает ожидающий черновик с бросками. При неопределённой доставке мастер может повторно показать сохранённый текст. Если черновик нужно исправить до публикации, `reopen --turn t001 --draft-sha <sha>` позволяет подготовить исправление с тем же ID хода и прежними бросками.

## Мир и перемотка времени

Событие задаётся полями `id`, `at`, `summary` и `visibility`. `based_on` может ссылаться на идентификаторы уже записанных событий, включая более ранние события в том же ходе. `operations` перечисляет последствия. Начальный набор операций из конфигурации получает идентификатор источника `campaign-setup`.

| Операция | Поля помимо `op` |
| --- | --- |
| `upsert_npc` | `npc` с `id`, `name` и опциональным `profile` |
| `set_fact` | `subject`, `name`, `value`, `visibility` |
| `delete_fact` | `subject`, `name` |
| `set_belief` | `actor`, `topic`, `belief`, `evidence`, `certainty`, `visibility` |
| `delete_belief` | `actor`, `topic` |
| `start_process` | `id`, `owner` (ID NPC), `goal`, `due_at`, `visibility`, `notes` |
| `reschedule_process` | `id`, `due_at`, `notes` |
| `finish_process` | `id`, `status` (`resolved` или `cancelled`), `outcome` |

Видимость бывает `gm_only` и `player_known`. Видимость события управляет выдачей его краткого описания, а видимость факта задаётся в самой операции. Источники знаний — `witnessed`, `reported`, `document`, `inferred`, `uncertain`. Уверенность — `certain`, `probable`, `uncertain`. Профили NPC, их убеждения и заметки процессов доступны мастеру. Если ход тайно завершает или переносит ранее известный процесс, результат доступен мастеру. Игрок узнаёт о нём через сцену или опубликованный факт.

`due_at` — ближайший момент, когда надо рассмотреть намерение NPC или ожидаемую доставку. Мастер может довести сцену до этой границы и остановиться. Для дальнейшей перемотки он включает в пакет хронологически упорядоченные события, в которых решает, чем завершился процесс или когда его следует рассмотреть снова. В одном пакете можно пройти несколько границ. Срабатывание календаря само по себе сохраняет процесс открытым.

## Память и продолжение

- `search "поисковые слова" --audience gm` ищет по подтверждённому тексту и вводу игрока. `entry turn <id>` или `entry event <id>` открывает исходную запись. Поиск по умолчанию показывает доступную игроку историю.
- `audit-handoff --state-dir <путь>` сверяет настоящий бинарный `state.json`/SQLite, закрытые архивы и при наличии текстовое состояние `FAST_SCENE`. Отдельно указывает `binary_verified`, `synchronized` или `text_ahead_unreplayed`; не позволяет восстанавливать сцену по устаревшему HOT. Это межсессионная проверка, а не дополнительный вызов на каждый игровой ход.
- `checkpoint next-chat.sqlite` делает согласованную копию SQLite вместе с рабочим черновиком и бросками. `python -m rpg_engine --db next-chat.sqlite verify` проверяет копию, после чего можно открыть её через `context`.
- `close-session archive/session-001.md --revision <n>` экспортирует сыгранное, проверяет неизменяемый архив, **автоматически уплотняет журнал закрытой сессии** и открывает следующую в подтверждённой сцене. Если первоисточник — очищенный экспорт, передайте проверенные дословные диапазоны через `--transcript`. Активная сессия всегда хранится полностью. Старые реплики восстанавливаются дословно через `entry`, полный поиск — через `search`/`recall` и отдельный индекс слов без копии текстов. Для старых закрытых сессий: `compact-history --through 2` (только при наличии совпадающего по SHA архива). См. [порядок перехода](docs/LONG_CAMPAIGN.md).

### Хранение кампании в приватном Git

Сохранение кампании публикуется в отдельной ветке, например `game-state/my-game`. Команды используют обычную аутентификацию Git. При первом сохранении укажите `--expected new`.

```bash
python -m rpg_engine git-save --remote git@github.com:sifiroth-gif/NPR.git --branch game-state/my-game --expected new
python -m rpg_engine --db restored.sqlite git-load --remote git@github.com:sifiroth-gif/NPR.git --branch game-state/my-game
```

Для доступа через файловое подключение GitHub крупный снимок дублируется сжатыми частями в `recovery/sqlite/`. Возьмите `state.json`, `parts.json` и все указанные части из одного коммита, сохраняя пути, затем выполните `python -m rpg_engine --db restored.sqlite restore-state <папка>`. Команда сверяет SHA-256 и манифест.

Для последующих публикаций укажите `--expected <head>` из последней загрузки или публикации этой копии. Движок проверяет идентичность кампании, поколение сохранения и SHA-256 базы. При конфликте откройте актуальную ветку в новой локальной копии и сверьте рабочие ходы перед продолжением. Для переноса ожидающего ответа вместе с бросками сначала опубликуйте текущее состояние в приватной ветке.

## Архитектура

| Модуль | Ответственность |
| --- | --- |
| `engine.py` | Ревизии, черновики, атомарная фиксация ходов, сессии и контрольные точки |
| `world.py` | Проверка событий и проекция фактов, знаний, NPC и процессов |
| `rng.py` | Версионированные воспроизводимые броски с закрытым ключом кампании |
| `history.py` | Запросы к SQLite FTS5 по записанным источникам |
| `git_state.py` | Проверка и перенос снимков через отдельную ветку Git |

Основа переноса — `world_state.py`, `history_index.py` и `rng_transaction.py` в исходном коммите [07b122a](https://github.com/sifiroth-gif/Bleach-RPG-/commit/07b122a5f9a93fde968f704c0fb69a9d349ffe38). Состояние, журнал, история бросков и черновик объединены в одной базе. Подтверждение обновляет состояние и журнал, индексирует новые записи и закрывает черновик одной транзакцией. Синхронизация Git переносит проверенный снимок.

```bash
python -m unittest discover -s tests -v
```
