# Быстрое сохранение ходов Шики — восстановленная цепь памяти (v3, 15.11.2026)

> Этот раздел имеет приоритет над устаревшим протоколом v2 ниже. Вся структура состояния — на приватной ветке `game-state/shiki`.

## Устранённая проблема

Текстовое состояние обогнало SQLite rev217; `LATEST_SHIKI_CHECKPOINT.json` устарел, а его упоминания в протоколе v2 вели к потере реального места и времени. `FAST_SCENE.json` содержал только три резюме, поэтому прежние события исчезали из оперативной видимости, хотя оставались в Git commit history. Отменённый ход `s03.text.081` и его исправленная версия получили один и тот же ID, что нельзя разрешать просто порядковым номером.

Восстановлено:
- `recovery/SESSION_003_RECOVERED_TEXT_070_085.json` — полные слова и игровые ответы 070–085 из исторических Git-коммитов; `081@void` помечен неканоническим.
- `recovery/fast_turns/s03.text.063.json` … `s03.text.069.json` и исправленная `s03.text.068.rev1.json` уже существовали.
- `recovery/ACTIVE_MEMORY_INDEX_1283_09_27.json` — индекс источников, фактов, персональных знаний, отмен и неснятых противоречий до хода 085.

### Источники

- Источник **текущей сцены**: `recovery/FAST_SCENE.json` и `cursor.at`.
- Источник **прошлого события**: указатель в `memory_sources` -> `ACTIVE_MEMORY_INDEX...` -> точный текст хода. `LATEST_SHIKI_CHECKPOINT.json` — только исторический материал до ~15:02 27.09.1283.
- Источник **знаний NPC**: реальная наблюдаемая сцена, доставленное сообщение/документ или корректно помеченная гипотеза из личного опыта NPC, НЕ GM секреты.
- Источник **утверждённого лора**: поздние прямые указания игрока и утверждённые карточки. Время и допуски исходят из канонических ходов.

### Ритм работы

- Один read + один update на обычный ход. При сомнении адресное чтение первоисточника сверх этого бюджета **не запрещено** — качество и правдивость важнее формальной цифры.
- HOT хранит не более шести последних кратких резюме и последний полный ответ. При накоплении шести новых ходов после последней архивации сначала сохранить их дословно в отдельный архив, обновить индекс/указатели, затем вытеснять из HOT.
- Перед ответом: `cursor.at` и `performance.game_time_now` равны; все `actor_*` находятся в реальных местах; статус согласия пациента и полные реплики игрока не подменены; неканонический `081@void` не попал в действующую историю; знаемые NPC сведения имеют источник. Наблюдаемая реплика NPC может быть ложью, но помечать её как утверждение.
- Межсессионное слияние SQLite: ходы 063–085 и дальнейшие только в подтверждённом порядке (исключая отмены), источники/свидетели и последствия отдельно. Запустить **реальное** `verify --full`, не менять ревизию фиктивно.

# Быстрое сохранение ходов Шики — v2 (14.11.2026)

## Применимость
**Согласованное правило игрока от 14.11.2026:** во время открытой сессии достаточно текстового чекпоинта после каждого хода. Его задача — удерживать точный текущий контекст, игровые последствия, состояние персонажей и незавершённые процессы, не перегружая окно чата. Обновлять SQLite на каждом ходе не требуется. **Полный replay в SQLite, verify, закрытие и уплотнение сессии выполняются при межсессионном переходе.** Не подменять текстовый чекпоинт официально подтверждённой ревизией SQLite.

Историческое описание сбоя ревизии 85 устарело: после межсессионного перехода II→III действующая проверенная SQLite находится на ревизии 217, сессия III, 26.09.1283 09:28:19. Дальнейшие текстовые ходы могут опережать её до очередного межсессионного обновления.

## Главное правило: один GitHub update на обычный ход
1. При входе в чат открыть **один раз** `recovery/LATEST_SHIKI_CHECKPOINT.json`, актуальную сцену, источники/участников по необходимости. Не читать всю историю и карточку повторно без причины.
2. Разрешить ход, подготовить текст ответа, зафиксировать в компактном `LATEST_SHIKI_CHECKPOINT.json` **точный ввод игрока, текущую сцену, последствия, позицию и знания NPC, неразрешённые линии, инвентарь, время, опубликованный текст** либо ссылку на него. Для разных смысловых статусов отдельно помечать `факт/показание/гипотеза`. Самого Шики не вести за игрока. Добавить новый последний элемент `recent_turns` и убрать самый ранний при превышении 6. Предыдущие версии сохраняет Git.
3. На **обычном** ходе вызвать ровно один `mcp__GitHub__update_file` для `LATEST_SHIKI_CHECKPOINT.json` с последним известным `content_sha`/blob SHA. Ответ об успешной записи с commit SHA и content SHA достаточен для ежедневной проверки; **не делать немедленного повторного fetch/readback**, если операция не дала сбоя. Использовать новый `content_sha` в следующем ходе, когда он известен.
4. Если нет достоверного `content_sha` (новый чат, потеря контекста) — один `fetch_file` перед `update_file`; при конфликте SHA перечитать и аккуратно повторить с учётом нового состояния. Не перетирать чужие правки.
5. Сохранять **одну полную точку восстановления в каждом Git-коммите**: прежнюю версию `LATEST` можно открыть через соответствующий commit GitHub. Полная историческая база из 97 источников и 124 открытых записей уже записана в коммите `2d5990e5d0507d98abe3962e0a90e3745eeb8348`, её blob SHA `2f85cb83c7aca51add54c6943235f24e7e6ce3ca`. Не удалять исходные 97 событий `campaigns/shiki/continuity/`.
6. В отдельные `continuity/` писать **не каждый ход**, а при смене сессии, крупном изменении канона, длительной перемотке, изменении правил, специальном `Сохранение`/экспорте или когда нужно полнотекстовое индексирование. После нескольких ходов при архивации учесть Git-коммиты и `recent_turns`. Нельзя утерять дословную игровую сцену — хранить её в текущем компактном документе и в истории Git-коммитов.

## Устойчивость контекста в течение сессии
- На каждом ходе обновлять компактное **оперативное состояние**: время и место, последний ввод и полный опубликованный ответ, последние 6 ходов кратко, состав сцены, здоровье/ресурсы/позиции, автономные дела, факты и неопределённости, статус опасных предметов.
- Не пересказывать в новом чате всю историю; брать короткую текущую сцену и адресные карточки/источники. По необходимости восстанавливать любой старый ход из истории Git-коммитов и межсессионного архива.
- Текущий активный журнал **не** уплотнять или чистить до закрытия сессии. В оперативном зеркале допустимо оставлять только 6 последних резюме: более ранние полные тексты сохраняются в истории Git и должны быть включены в replay при межсессионном переходе.
- Пользователю показывать игровой ответ без повторяющейся технической приписки о несовпадении ревизий. Сообщать о сбое только при реальной потере записи, конфликте или прямом вопросе.
- Для межсессионного переноса собирать все ходы со времени последней подтверждённой ревизии SQLite **в хронологическом порядке**, сохранять точные тексты и источник каждого хода, не ограничиваться шестью последними.

## Восстановление
- Сначала прочесть `recovery/LATEST_SHIKI_CHECKPOINT.json` (основной источник текущей сцены; `game_at`, `scene`, `latest_player_command`, `recent_turns`, `last_response_text`).
- Для старой подробной хронологии — `legacy_checkpoint.commit_sha` и `legacy_checkpoint.blob_sha`, прежние файлы из `chronological_sources`; для последнего архивированного эпизода — `latest_source_path`.
- Если требуется точный промежуточный ход между редкими архивациями, проверить Git-историю `LATEST`, где каждый успешный `update_file` создаёт отдельный коммит. Не объявлять старый SQLite текущим каноном.
- На ручной проверке `Сохранение` / конце сессии выполнить отдельный `fetch_file` и контроль последней сцены; сохранить при необходимости архив/индекс.
- Повышенный риск потери истории при принудительном переписывании ветки: не применять force-push и не переписывать историю Git. Нельзя утверждать о 100% долговечности без форензического снимка/SQLite.

## Межсессионный переход
1. Сверить последний проверенный SQLite `state.json` с журналом всех текстовых ходов после этой ревизии; выявить отмены/исправления, сохранить поздний канон.
2. Воспроизвести в движке в порядке публикации: `prepare`, подтверждение уже показанного игроку ответа, `confirm`, с сохранением фактических времён, действий NPC и событий.
3. Выполнить `verify --full`, закрыть завершённую сессию с дословным архивом, уплотнить только **закрытый** журнал, открыть следующую сессию.
4. Опубликовать проверенную SQLite, `state.json`, `recovery/sqlite` в одном согласованном состоянии с проверкой SHA. После этого обновить текстовый checkpoint на новый базовый revision. Если воспроизведение неполно, честно оставить статус pending, не выдавать текст за подтверждённую SQLite.

## Бюджет операций
- Обычный ход с известным SHA: **1 update_file**, **0 проверочных fetch**.
- Новый чат или неизвестный SHA: **1 fetch_file + 1 update_file**.
- Критический поворот/ручное сохранение: отдельные проверочные операции по необходимости.
- Не задерживать публикацию текста ради повторных чтений, если подтверждённый GitHub commit уже получен.

_Этот протокол ускоряет временное текстовое сохранение и не подменяет целевую транзакционную SQLite-архитектуру из README.md и AGENTS.md._
