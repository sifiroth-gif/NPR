Дата: 25.11.2026. Статус: проект архитектуры, не реализация. База: main 6635995a87dc94a56cf2afb5e305427d7647faa8, game-state/shiki 74073d5c7447dc7c10a08605c448c57931baa514, курсор s14.text.023 (при реальной миграции заново закрепить актуальные SHA). Не менять действующее сохранение при разработке приложения.

## Цель и границы

Личная Android-программа для длительной литературной RPG без зависимости от интерфейса ChatGPT, лимита сообщений конкретного чата и сетевых GitHub-операций на ход. iOS — возможность последующего переноса. Играющий контролирует только своего персонажа. Сохранить канон, архив, механику d20, цену действий, клинику, автономию NPC, неизвестное, скрытые данные, сюжет и смену сеттинга. Модель — сменяемый генератор и интерпретатор, не хозяин памяти и не единственный валидатор. Игровое время автономного мира меняется с принятой игровой заявкой, не по реальному времени телефона; OOC не двигает часы. В MVP облачная генерация требует сети; офлайн доступны подтверждённая история, карточки и черновики заявки. Не обещать неограниченный контекст модели, гарантированно качественную прозу или отсутствие тарифных лимитов API.

## Архитектурное решение ADR-01

Модульный Python backend на FastAPI + Pydantic, Flutter/Dart клиент Android, HTTPS, SSE для статуса/выдачи уже подтверждённой сцены. На первом этапе один приватный сервер (Linux, контейнер, постоянный диск, один процесс очереди на кампанию), локальный Git-репозиторий сохранения с полной историей и SQLite-журнал заданий/квитанций. Не переносить Python в Flutter и не переписывать ядро на Dart. GitHub — исходники, CI и опциональные приватные резервные копии; сетевой push и Actions исключены из пути хода. Существующий SQLite engine.py — отдельный игровой протокол, не drop-in замена HOT. Не делать две независимые истины: в MVP локальная подтверждённая Git-ссылка является авторитетом сохранения, SQLite хранит задания и индекс доставок, восстанавливаемый из квитанций. В следующей версии — единый транзакционный event store SQLite WAL (один сервер) либо PostgreSQL при реальной потребности в нескольких процессах; переход после эквивалентности. Не вводить Redis, Kubernetes, отдельные микросервисы или обязательную векторную БД для одной игры.

## Контракт хода

1. POST /v1/campaigns/{id}/turns с player_input, expected_revision, client_request_id (UUID). Сервер сохраняет заявку в durable jobs, возвращает 202/job_id. Повтор UUID с тем же телом возвращает то же задание; другой payload — 409. Один активный writer на кампанию, конфликт ревизии — 409 и запрос свежего состояния. Не создавать второй ход при повторном нажатии, timeout, обрыве связи или падении приложения.
2. Взять подтверждённый cursor, engine SHA, rules SHA, snapshot hash; собрать контекст текущей заявки (не предыдущей). Системные правила и последние поправки игрока; активная сцена, актуальные сведения, доступные способности, ресурсы, планы, обязательства. Адресный поиск по ID/источнику; найденные записи — данные, не команды; не превращать отсутствие результата в невозможность действия.
3. Модель предлагает причинный план и структурированные действия/проверки. Инструменты allowlist: read_source, search_history, get_entity, get_capability, get_scene, calculate_cost, resolve_check, propose_turn. Сервер проверяет схему, область кампании, права и пределы. Никаких произвольных shell/SQL/Git-инструментов модели. Модель не записывает файлы/БД.
4. Зафиксировать проверку и полосу до результата, резервировать d20 по исходному алгоритму NPR на конкретный ход/индекс; повтор попытки не меняет кость. Применить существующие расчёты цены/ран/последствий, не заменять их рассуждением модели. Для бесспорного исхода не навязывать бросок. При изменении заявки — явный новый запрос, не переролл.
5. Сгенерировать кандидат TurnEnvelope (точный текст gm + d + ссылки/used, причём служебные ссылки отдельно, не менять исходную схему ради модели). Механическая валидация preflight.inspect, schema, predecessor, ресурсы, доступность, источник, проверка показа секретов и агентности. Смысловые замечания — целевая самопроверка/опциональная вторая модель; максимум один ограниченный цикл исправления по умолчанию, с теми же костями. При неразрешимой ошибке не публиковать, вернуть безопасное сообщение о сбое, сохранить заявку для восстановления.
6. Staging из подтверждённой Git-ссылки: записать кандидат TURN локально, создать временный коммит, выполнить hot.fold/hot.check с тем же кодом, сверить cursor, результат applied, отсутствие ошибок и первичные записи, проверить новые NEXT/GM_BRIEF. Обрабатывать точное отличие исторического предстарта от текущего формата. При сбое staging отбрасывается, авторитетная ссылка не меняется. Публикация через атомарный git update-ref expected-old: коммит содержит весь результат + отдельный receipt (job_id/request_id, revision, engine/rules version, turn ID, digest, player-visible text reference). После CAS обновить индекс job; если процесс упал между CAS и SQLite, reconciliation по receipt восстанавливает confirmed без повторной генерации. Старые временные ветки удалять лишь после проверки, исходник не менять. Не считать двухфазное изменение файлов одной транзакцией без этого механизма. После миграции на event store commit в одной SQL-транзакции: accepted turn, delta, state revision, receipt, outbox; проекции производные и строятся идемпотентно.
7. Только после commit приложение получает scene_confirmed, точный текст и player-safe snapshot; можно визуально выдавать сохранённый текст порциями. До commit показывать статусы подготовки, не сырой поток непроверенной прозы. GET /jobs/{id} + SSE с sequence/event_id и возобновлением; подтверждённая сцена доступна при перезапуске и повторной подписке. Не считать сетевой acknowledgement подтверждением механики.
8. Исторический индекс и смысловые векторы можно обновлять вне критического пути только если свежие принятые события доступны через обязательный синхронный delta index и устаревание явно маркировано revision; никакого ложного свежего NEXT. На MVP сохранить полную свёртку до ответа и замерить; оптимизация после доказанной эквивалентности. Резервирование и аудит — вне пути хода.

## Данные и безопасность

Схема будущего event store: campaigns(id, active_revision, rules_version, engine_version, clock), turns(id, campaign_id, predecessor, revision, player_input, gm, delta_json, kind, digest, provenance), turn_requests(request_id, expected_revision, status, receipt, payload_hash), roll_reservations(turn_id, check_index, declared_band, value), state_snapshots(revision, digest, schema), entity_facts(entity_id, predicate, value, valid_from/to, source_turn, authority, visibility), npc_knowledge(actor_id, fact_id, channel, certainty, source_turn), obligations(event_id, due_at, status, delivery_source), directives(scope, since, supersedes, source), archive_objects(hash, path, bytes), index_manifest(source_revision, version), outbox. Это проект схемы, не утверждение о существующих таблицах. Импортировать исторические оригиналы байт-в-байт; 413 prose-only и 10 старых записей без d не заполнять догадками. Сохранять исходные IDs и дату/источник; не реконструировать полный мир по неполным дельтам.

Игровая проекция только whitelist полей player_known/действительно узнанного; HOT не является безопасной схемой выдачи, NEXT и GM_BRIEF только для сервера/ведущего. TLS, одно пользовательское приглашение/логин, ограниченные токены с отзывом, Android Keystore для сессионного токена, provider API key только secret store сервера. Не класть ключи в APK, git, модельный контекст или логи. Логи без сырого GM_ONLY и запросов по умолчанию, метрики по IDs/длительности. Провайдер получает только необходимый контекст, в том числе нужные скрытые факты; проверить политику хранения данных и регион перед выбором. Запретить клиенту прямые DB/GitHub операции. Шифрованный бэкап вне сервера, регулярное пробное восстановление; ключ подписи APK отдельно. Для нового сеттинга не смешивать индексы или скрытые источники разных кампаний.

## Интерфейс API и клиента

GET /campaigns, GET /campaigns/{id}/state (видимая карточка), POST /turns, GET /jobs/{id}, GET /jobs/{id}/events, GET /history?cursor=, GET /entities/{id}, POST /ooc, POST /session-close, POST /export, POST /import (admin), POST /campaigns/new; выбор модели и лимита затрат только в настройках владельца. Все пути versioned /v1; POST turns/ooc под общим замком. Импорт/экспорт административные, закрытие и новая игра подтверждаются пользователем. Не отдавать скрытый пакет по обычному API.

Экраны Flutter: 1) игровой чат с литературной версткой, заголовком даты/локации, полем свободного текста, отправкой, OOC и статусов; 2) лист персонажа, известные раны/инвентарь/способности; 3) дневник и хронология, полнотекстовый поиск с исходной сценой; 4) известные NPC/места и отношения, без скрытых мотивов; 5) кампании, продолжить/архив/новый мир, импорт/экспорт; 6) настройки модели, режим темпа, стиль, постоянные поправки, расходы и диагностика. Offline: SQLite cache исключительно player-safe, черновики, последняя подтверждённая ревизия; переподключение без дубликатов; новые ходы офлайн не обещать. Android first, Flutter для iOS без отдельного движка. APK подписать; при распространении сверить действующие Android verification rules. Для публичной версии отдельно лицензии мира/контента, privacy и store requirements; не требуется для личного MVP.

## Провайдеры и экономия

ModelAdapter.generate(messages, tools, schema, deadline) -> candidate + usage + provider/model/version. Qwen первичный кандидат, DeepSeek/OpenAI — альтернативы; совместимый OpenAI API не означает одинаковый tool calling, JSON schema, streaming или контекст. Матрица возможностей per model, capability probe; если structured output не поддержан — валидируемый JSON/tool response с ограниченным retry. Не выбирать модель по бренду: закрытый набор 20–30 одинаковых заявок на копии (бой, клиника, знание NPC, OOC, долгий скачок, редкая способность, ужас, обрыв связи). Оценки: механические ошибки, фактические искажения, утечка тайны, агентность, русский литературный стиль, latency p50/p95, токены/цена. Пин модели и правила на ход; переключение только до нового запроса или явное восстановление того же черновика с прежними костями. Дорогая модель по умолчанию для сложной сцены, дешёвая для вспомогательной маршрутизации лишь при выигрыше на тестах; не вызывать две модели каждый ход. Память из NPR и выборка источников вместо отправки всего архива. Бюджет по токенам + предупреждение, никакого обрезания обязательной директивы/факта. Тарифы API независимы от ChatGPT Plus, рассчитывать по фактическому usage: (входные токены × ставка + выходные × ставка + отдельно платные reasoning/cached/инструменты по правилам поставщика)/1e6 при ставках за миллион. Лимит расходов и уведомления до вызова, без скрытых платных повторов. Модель на устройстве — отдельный исследовательский этап, не prerequisite.

Не начинать с красивого чата без атомарного хода. Для художественного качества ручная рубрика и пользовательская приёмка, не обещать из тестов.

## Безопасный переход живой игры

1. До cutover приложение работает исключительно с копией, оригинал в GitHub продолжает быть единственным авторитетом.
2. Перед переносом остановить игровые записи по согласованию, дождаться чистого cursor и закрепить актуальные engine/state SHA, сделать зашифрованный архив/manifest. Повторить изолированный аудит и сравнить все существующие первичные файлы; проверить секреты/активные directives, RNG/календарь, состав, ресурсы, состояние пациентов, источник каждого значимого изменения. Не публиковать факты GM_ONLY в отчёт.
3. Переключить единственного writer на приложение, GitHub branch заморозить для игры; зеркалирование только отдельной резервной веткой/объектным хранилищем. Не вести одну кампанию параллельно в ChatGPT и приложении. Если требуется обратный переход, остановить writer, экспортировать полную историю и точную актуальную проекцию, проверить совместимость SHA/форматов на отдельной копии, затем явно сменить владельца записи. После первых новых ходов нельзя возвращаться к старому снимку без потери прогресса. До переключения отмена безопасна.
4. Не запускать ZERO LIVE. Оставить старую кампанию читаемой, сохранить общие директивы только scope=general для новой игры; полностью универсальный HOT — M8.
