# Длительная текстовая RPG

Одна приватная SQLite хранит сыгранный журнал, текущие факты, знания NPC, открытые дела, ожидающий ответ и броски. Смена чата восстанавливает позицию из этого состояния. Код, пакеты сеттингов и планы хранятся в основной ветке. Ветки `game-state/<id>` содержат экземпляры кампаний.

## Вход в сцену

```sh
python -m rpg_engine --db campaign.sqlite verify
python -m rpg_engine --db campaign.sqlite gm-packet
python -m rpg_engine --db campaign.sqlite gm-packet --mode scene --actor guard
python -m rpg_engine --db campaign.sqlite gm-packet --mode montage --target 0001-07-03T13:00:00
```

Обычный ответ использует короткий `focus`: последние реплики, их адреса, подтверждённое время, участников, известные им сведения, актуальные поправки и ближайшее дело мира. Режимы `scene` и `combat` разворачивают нужные карточки. `scene`, `montage` и `handoff` подхватывают условный план текущей сессии из пакета сеттинга. При возвращении персонажа или спорном воспоминании выполнить `recall`, открыть `entry` и сверить позднейшие поправки.

Поле `scene` в новом пакете хода сохраняет текущий состав и тип игрового события: `{"id":"scene.1","actors":["guard"],"beat":"decision","focus":"У двери появился свидетель"}`. Порядок `focus → scene → montage` определяется последствиями, масштабом времени и выбором игрока. Три подряд помеченных бытовых хода дают ведущему повод перейти к содержательному событию. Для опасности укажи боевой контекст и физическое окно ответа. План сессии и предупреждения о темпе не двигают часы и не разрешают исходы.

## Память и поиск

| Команда | Использование |
| --- | --- |
| `entry turn turn.42 --audience gm` | Полная сохранённая запись, в том числе исходный ввод игрока |
| `recall "пропуск башня" --audience gm --session 1` | Точные слова, поиск по близким формам, ограниченные исходные выдержки |
| `recall --entity guard --audience gm` | Явные источниковые связи персонажа, без угадывания по упоминаниям имени |
| `memory --actor guard --audience gm --at 0001-07-02T14:48:00` | Только личные записи дозорного, существовавшие к указанному времени |
| `memory --key tower.entry-rule --history --audience gm` | История версий рассмотренного правила |
| `record-review event.json --revision N` | Поправка игрока, проверенная заметка или будущий план с первичным источником |

`recall` возвращает ID, сессию, время, координаты и хеш источника. Граф показывает явные связи между событиями. Поисковое совпадение подлежит чтению в оригинале. Сохранённые реконструкции помечены отдельно. Параметр `--include-superseded` возвращает также поправленные события. Применять `supersedes` только к конкретной отменённой записи, а точечную замену помечать версией памяти.

Память `remember` хранится с указанием источника и статуса `open/resolved/retracted`. Категории охватывают канон, линии, обязательства, сцену, сессию, NPC и пробелы источников. При замене укажите `previous` с текущим ID события. Источниковый приоритет возрастает от `plan` через `setting` и `played` к `player`. Участник получает убеждение через наблюдение, сообщение, документ или вывод по своим данным. Личный поиск выводит историю таких записей и маршруты доступа без общего текста тайной сцены.

В базовом режиме работают SQLite FTS5/BM25, явные связи и фильтры по времени. Режим hybrid добавляет локальный семантический индекс. Для него установить современный `sentence-transformers` и заранее разместить локальную копию multilingual-e5-small. Определить SHA через `model-id /path/to/e5`, закрепить его в своём окружении и выполнять:

```sh
python -m rpg_engine semantic-index recall.sqlite /path/to/e5 --model-sha "$NPR_MODEL_SHA"
python -m rpg_engine recall "старый долг" --audience gm \
  --semantic-cache recall.sqlite --model /path/to/e5 --model-sha "$NPR_MODEL_SHA"
```

Кэш производный, привязан к экземпляру и составу журнала. Переиндексация использует уже закодированные неизменившиеся окна. Сканирование выполняется на CPU, а точные отрывки берутся из живого журнала. При устаревшем кэше использовать обычный поиск или явно обновить индекс. Веса и индексы не нужны для запуска игры.

Модель памяти учитывает ошибки доступа к длинному контексту и пользу адресной индексации с учётом времени. Источники: [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/), [LongMemEval](https://proceedings.iclr.cc/paper_files/paper/2025/hash/d813d324dbf0598bbdc9c8e79740ed01-Abstract-Conference.html), [SQLite FTS5](https://www.sqlite.org/fts5.html), [Sentence Transformers](https://www.sbert.net/docs/package_reference/sentence_transformer/model.html).

## Самостоятельный мир

`world-queue <until>` выдаёт очередность дел до намеченного времени. Чтение не тратит игровое время. Ведущий выбирает действие из личных целей NPC, доступных сведений, условий и ресурсов. До истечения ближайшей границы можно вести локальный диалог. Для монтажа решать дела по порядку, смотреть пересчёт доступности после каждого результата и останавливаться у первого значимого выбора игрока. На самой границе можно показать угрозу и дождаться реакции. Пройти границу активного дела можно после его рассмотрения и сохранения результата.

- `start_process` задаёт владельца и ближайший срок. В `configure_process` добавляются предпосылка, фаза, существенность и возможные решения. У каждого решения есть намерение, последствия и условие завершения либо следующий срок. `requires` проверяет точное значение факта или личного убеждения владельца. `effects` задаёт явное изменение фактов, включая затраты. Новая фаза требует нового рассмотренного плана. Троекратное одинаковое откладывание без изменений требует пересмотра.
- `take_process_step` фиксирует конкретное решение в срок, с ID плана и объяснением. Если вариант оставляет игроку окно реакции, предъяви его в видимой сцене, дождись ввода и сошлись на событие показа в `window_resolved_by`.
- `schedule_message` проверяет личный источник отправителя, планирует доставку по указанному каналу и допускает обман с объяснённой целью. `deliver_message` проверяет наступление срока и доступность канала. Доставленное сообщение другому NPC включает явную запись `set_belief` и маршрут `reported`. Доставка игроку показывается в сцене, а реакцию выбирает игрок.
- `update_npc` ссылается на предыдущую версию профиля и сыгранный опыт через `based_on`. Профиль хранит устойчивые мотивы, отношения, манеру речи и ограничения. Текущее решение следует из ситуации и опыта. Важным NPC нужна отдельная память об обязательствах и переменах отношения. Фонового NPC достаточно назвать и дать ему понятную цель.
- `assert_state` связывает исход сцены с точным фактом или убеждением и при необходимости с ID источника. Подготовка отклоняется, если утверждение опирается на устаревшее значение. Повторная проверка выполняется при подтверждении в той же транзакции, что запись последствий.

Пример частного события для решения в установленный срок:

```json
{
  "id": "patrol.decision.01",
  "at": "0001-07-03T13:00:00",
  "summary": "Патруль сменил маршрут после доклада.",
  "visibility": "gm_only",
  "based_on": ["patrol.plan.01", "patrol.report.01"],
  "operations": [
    {"op": "take_process_step", "process": "patrol", "option": "reroute",
     "plan_source": "patrol.plan.01", "reason": "Доклад дозорного и доступный обход"}
  ]
}
```

Цепочка исполнения проверяет точные поля, ссылки, время и последствия. Мотивы, правдоподобие новых предпосылок, границы знания и смысл художественного текста сверяет ведущий. Для причинного боя действуют [механика боя](COMBAT_MECHANICS.md), пространство, доступные признаки, время реакции, ресурс и анатомические последствия. На остаточную неопределённость используется сохранённый RNG по ID хода и проверки. Он живёт в том же приватном снимке, что и сцена.

## Продолжение, проверка и смена сеттинга

- На новый ход создать `prepare` с точным ответом. Подтверждать только показанную редакцию. Перед игровым ходом в новом чате сверить `gm-packet --mode handoff`: отдельные подтверждённый текст, ожидающий черновик и устойчивые броски. Игровое время не течёт между чатами само.
- Короткое добавление сыгранного, передача контекста и полный чекпоинт имеют разную стоимость. В рамках непрерывной сцены переиспользовать локальную проверенную базу. Сохранять на причинно значимых границах и перед потерей контекста. Ходы с зарезервированным броском и опубликованные черновики, которые нужно перенести, требуют проверенной долговременной записи. `git-save` проверяет SHA предыдущего снимка, экземпляр и ожидаемый Git HEAD. GitHub Actions можно использовать как резерв при недоступном прямом переносе.
- Для среды с подключённым GitHub и без авторизованного Git CLI используй Git Data API: прочитай HEAD ветки, загрузи оба файла из этого коммита, проверь манифест и выполни `export-state` на рабочей копии. Сверь префикс истории через `git_state.require_prefix`. Опубликуй бинарный blob и манифест одним дочерним коммитом без форсирования ссылки. Затем заново прочитай HEAD, сравни SHA-256 обоих файлов и проверь базу.
- `verify --full` воспроизводит факты, память и процессы из журнала, проверяет хронологию, источники, FTS и RNG. `close-session export.md --revision N` сохраняет исходный диалог и хеш экспорта, затем открывает следующую сессию в той же точке. `export-session export.md --session N` доступен для проверки и чтения. Утверждённые последствия, незакрытые линии и память сохраняются. Следующая сессия получает план исходя из текущих дел, а смена чата продолжает прежнюю.
- `new-setting /path/to/setting` создаёт чистый пакет для другой игры. Укажите новый ID и тот же ID в `scene.json`, заполните стартовые правила, персонажей и часы, выполните `init` на новом пути и используйте свою `game-state/<id>`. Для переноса универсального ядра добавьте `--portable`. Команда экспортирует движок, документацию и пустой шаблон.

Основной архитектурный источник: [Bleach-RPG- @ 07b122a](https://github.com/sifiroth-gif/Bleach-RPG-/tree/07b122a5f9a93fde968f704c0fb69a9d349ffe38). Перенесены принципы `gm_local_continuity`, `gm_adaptive_pacing`, `gm_event_graph`, `gm_hybrid_recall`, `world_autonomy`, `npc_psyche`, `session_contours` и транзакционного RNG. В NPR их реализация опирается на общую SQLite-транзакцию и существующие контракты боя и знаний.

## Восстановление из первичного лога

Для выгрузки с отменёнными сценами и техническими обсуждениями вычитайте первичный экспорт. Воспроизведите известные последствия поверх проверенной копии текущей базы с указанием источника. Закройте сессию командой `close-session --revision <n> --transcript reviewed.json archive/session-001.md`. JSON содержит `format: "npr-session-transcript/1"`, `session`, `source`, `source_sha256` и `passages`. Каждому фрагменту задайте `role` (`player` или `gm`), игровое `at`, исходные `text` и `ranges`, а также массив идентификаторов `entities`. Диапазон задаётся четырьмя числами, начиная с единицы: строка и столбец начала, строка и столбец исключённого конца.

Сохранённый индекс возвращает `transcript.s<сессия>.<порядок>` через обычные `search` и `recall`; полная запись доступна по `entry event <id>`. Это текстовые источники, их добавление не запускает игровые последствия и не передаёт знания NPC. Старые квитанции ходов остаются доступны по ID. `verify --full` сверяет итоговый экспорт и контрольные суммы точных диапазонов. Повтор закрытия с той же ревизией и тем же содержимым безопасен.

`gm-packet --mode handoff` даёт только нужный для продолжения конец подтверждённого хода. Ожидающий черновик выдаётся дословно, с квитанцией для публикации. Полный план читается при входе в новую сессию; в обычной сцене нужны участники и ближайшие последствия. NPR уже использовал подход раздельного сохранения и чтения контекста. Для проверки границы между подтверждённым каноном и подготовкой сопоставлен [межсессионный цикл исходного проекта](https://github.com/sifiroth-gif/Bleach-RPG-/blob/main/docs/GITHUB_INTERSESSION_TRANSITION.md).
