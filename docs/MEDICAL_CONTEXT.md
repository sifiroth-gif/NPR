# Медицинский контекст C2

NEXT.medical — производный клинический снимок независимо от активного боя.
Схема: patients.<id>.w — строки по fields (where, severity, lost, turn, bleed,
recovered_at), loss — отдельная системная кровопотеря. null означает отсутствие
записи. other_ids — старые раны вне выбранных пациентов, открыть HOT/источник
по необходимости. Текущий набор включает Шики, присутствующих, пациентов с
ранами текущей сессии, даже перенесённых в другую комнату. Не обещает доступ.
Маршрутизатор при медицинской заявке даёт полный список, комплект, чакру и
адреса источников. В обычном чате применить контракт без вызова Python.
При отставании свёртки медицинский снимок снимается: учесть подтверждённые
дельты локально, неизвестное проверить, не повторять прежний дефицит как факт.

Пример сыгранного источника: s14.text.021, s14.text.023 — Минасэ после
восстановления проводимости двигает конечностями, остаточный парез и
сенсорный дефицит, ходьба не проверена, дыхание сохранено, рана закрыта.
Это не полное исцеление. Оператор сети имеет отдельную тяжёлую рану и
кровопотерю. s10.text.102 и s14.text.023 — переносные средства, стерилизация,
раздельное хранение использованных расходников; точный остаток неизвестен.
Не присваивать новым результатам численные значения без проверки.

С s14.text.024: начало восстановления после прекращения кровотечения
привязано к времени гемостаза; остаточная кровопотеря продолжает учитываться
после удаления последней раны. Существующая игровая шкала и интервал 6 часов
не меняются; это абстракция состояния, не медицинская норма. При сгустке
среди последовательных проверок нагрузка пересчитывается, закрытая рана
больше не кровит. Старые сыгранные ходы и их исходы не пересчитываются по
новым правилам. Явное blood — самостоятельное восполнение, не эффект
обычного восстановления ткани. При конфликтующем all/where лечение
не применяется. Условия и объём медицинской чакры — MEDICINE/COMBAT/B1;
C4 проверит цену, соответствие заявке и запись до отправки.
