# Перенос сеттинга без уничтожения кампании

Безопасный путь — отдельный каталог и новая ветка. Не очищать game-state/shiki, не переписывать историю.

## Проверяемый SQLite-перенос

```bash
python -m rpg_engine new-setting /path/to/new-game --portable
cd /path/to/new-game
# Изменить campaign.json и scene.json: новый одинаковый ID.
python -m rpg_engine init campaign.json
python -m rpg_engine gm-packet --pack scene.json
python -m rpg_engine verify
```

Новая база с ревизией 0, без NPC/фактов прежней игры; существующий каталог не перезаписывается. Экспорт включает код, LONG_CAMPAIGN и исторический COMBAT_MECHANICS, пустые campaign.json, scene.json, sessions; не копирует recovery, archive, memory, campaigns, .github, .git. Код содержит адаптеры Шики; чистые данные не означают независимость HOT. Публикация отдельного SQLite-снимка: README, git-save --expected new на game-state/<id>.

## Новый живой HOT-сеттинг (ещё требует адаптации)

1. Закрепить SHA кода и подтверждённого состояния старой игры, проверить архив/хеши и доступ. Имя будущей архивной ветки не доказывает резервирование.
2. Создать отдельные правила, BOOT, календарь, способности, карту мира, цены, боевые правила, сущности, знания. Переносить только явно размеченные активные директивы scope=general с источниками; неизвестный scope исключить.
3. Проверить hardcoded Shiki/Nemera/Naruto в hot.py, fight.py, canon.py, lore.py, nextpack.py, limits.py и workflow. Новый HOT seed и первый валидный TURN, проверка тайны, автономии, памяти, CAS/lag и fold на отдельной копии. hot-bootstrap мигрирует FAST_SCENE, не создаёт новую произвольную HOT-кампанию.
4. Настроить отдельный workflow и внешнюю инструкцию проекта; тесты и изолированная свёртка до публикации. Новую игру запускать по отдельному решению игрока. Старую восстанавливать с её неизменённой ветки и совместимым SHA кода.

## Протокол ноль

LIVE=False. handle составляет план/отчёт и гасит заявку, не архивирует и не очищает; mode=live тоже не запускает очистку. Архивная ветка в отчёте — предлагаемое имя, не созданная копия. Проверка по хешу; ввод остаётся в Git-истории, не использовать канал для паролей. Реальное архивирование/очистка/переключение — отдельное решение и проверка.

## Развёртывание

AGENTS main авторитетен, копия в состоянии может отставать. BOOT на main; внешнюю инструкцию проекта обновляет владелец. Push-workflow исполняется из ветки события; шаблон main не меняет game-state/shiki. При штатном согласованном обслуживании перенести проверенное удаление второго recall_audit, сверить HEAD и результат. Не инициировать живую свёртку ради теста.
