# Быстрый цикл сцены Шики: GitHub-only fallback

Дата принятия: 15 ноября 2026 года. Кампания: `naruto-shiki`, ветка `game-state/shiki`.

Этот режим действует **только** когда проверенная действующая SQLite не может быть запущена из чата: бинарный снимок остался на ревизии 217, а сыгранные текстовые ходы сессии 3 пока ожидают межсессионного воспроизведения. При доступной актуальной SQLite приоритет у `gm-packet → prepare → публикация точного текста → confirm → verify`. Быстрый текстовый режим **не выдавать за подтверждённую ревизию SQLite**.

## Актуальная точка восстановления

В приватной ветке:

- `recovery/FAST_SCENE.json` — **короткое оперативное состояние** и указатели; читать в начале каждого обычного хода. Не считывать длинный `recovery/LATEST_SHIKI_CHECKPOINT.json` без конкретной причины. Текущий переход выполнен после **`s03.text.063` в 15:02 27.09.1283**; следующий ID `s03.text.064`.
- `recovery/fast_turns/s03.text.NNN.json` — **неизменяемые точные** оригинальный ввод пользователя и полный опубликованный ответ ведущего; файл `s03.text.063.json` содержит дословную копию последнего хода до оптимизации.
- `recovery/LATEST_SHIKI_CHECKPOINT.json` — базовый длинный чекпоинт состояния до перехода, хранит старую сцену, сводки прежних 63 ходов и пути к канону. **После включения FAST_SCENE не обновлять его на каждом ходе**, не считать его новее короткого состояния. Не утверждать, что текстовые ходы 1–62 уже полностью воспроизведены в SQLite.
- Скрытый сюжет, карточки и исходные доказательства — по указанным в `FAST_SCENE.gm_private_refs` путям, только по необходимости.

## Один обычный ход: два инструментарных этапа

1. **Одно чтение.** GitHub `fetch_file` только `recovery/FAST_SCENE.json` на ветке `game-state/shiki`; запомнить `sha`, `cursor.last_turn_id`, `cursor.next_sequence`, актуальное игровое время. Лор/NPC открывать *адресно* лишь при появлении значимого нового факта или участника. Не повторять считывание README/AGENTS, десятков карточек или длинного чекпоинта.
2. **Разрешить ход.** Определить непосредственно доступное Шики, намерения NPC, последствия и время по заявке игрока. Время при чисто мастерском/OOC разговоре не меняется. Написать один полный окончательный ответ. Шики управляет только игрок; закрытые сведения не утекать в диалог.
3. **Один пакет записи.** В **одном** вызове `functions.exec` выполнить последовательно:
   - `tools.mcp__GitHub__create_file({repository_full_name:"sifiroth-gif/NPR",branch:"game-state/shiki",path:"recovery/fast_turns/s03.text.064.json",content:<полный JSON>,message:"..."})`. Поля: `format:"npr-immutable-turn/1"`, `turn_id`, `previous_turn_id`, `at`, `player_input` (точный), `exact_visible_gm_response` (точный), `summary`, `events` (при наличии), `published_status:"prepared_to_show"`; никакого создания копии с новым ID при сетевой ошибке без проверки существующего файла. Не писать неизвестное как факт.
   - `tools.mcp__GitHub__update_file({repository_full_name:"sifiroth-gif/NPR",branch:"game-state/shiki",path:"recovery/FAST_SCENE.json",sha:<sha из первого чтения>,content:<JSON с новым cursor, NPC, clues, scene, latest immutable path, короткими последними 4–6 summary>,message:"..."})`.
   - Вернуть лишь ID, статус обоих действий и новую дату. Отправить пользователю **ровно** текст из `exact_visible_gm_response`.
4. **Частичная ошибка.** Если точный ход создан, а FAST_SCENE не обновился — прочитать точный файл, обновить FAST с корректным SHA и сверить. Если операция создания выдаёт «уже существует», прочитать уже существующий ID, сравнить оригинальный ввод и точный текст; не повторять игру. Не объявлять «сохранено» при неудаче. Нельзя заменять или удалять уже опубликованный ход без явной поправки с новой ссылкой.
5. **Проверка.** Инварианты на каждом ответе: предыдущий ID совпадает, `next_sequence` монотонен, время не идёт назад, `FAST_SCENE.history.latest_immutable_turn` совпадает с сохранённым ходом, полная опубликованная реплика равна содержимому файла. Обратное считывание/полная проверка — каждые 5 ходов, при конфликте/важной необратимой развязке, после смены чата и перед межсессионным переносом. Полный `verify` SQLite после воспроизведения, не ежедневно ради одной реплики.

**Преимущество:** один лёгкий fetch (~12 КБ вместо ~68 КБ) и последующий последовательный пакет двух GitHub-записей вместо повторного чтения большой базы, нескольких карточек, записи счётчика и повторного чтения чекпоинта. Точные тексты не стираются из активной истории, потому что лежат в неизменяемых файлах. Вызовов к GitHub **в стандартном ходе три внутри двух обращений к инструментарию**, без дополнительной перепроверки каждого обычного хода. Фактическую задержку ещё нужно оценить на следующих ходах; обещания конкретного времени нет.

## Счётчик Договора Семи Запоров

Чистое течение игрового времени **не требует записи** `PACT_BURDEN_LIVE.json`. Пассивную нагрузку вычислять из неизменного `bound_at=0007-09-27T06:30:19`:

`P = min(100, round4(0.75 × elapsed_game_seconds / 86400 + confirmed_forbidden_points))`.

Реальные попытки, тренировки, освоение и применение **Ситона** и **Бётона** имеют отдельные очки и уникальные события, поэтому записываются в долговременный событийный журнал и обновляют накопленные `confirmed_forbidden_points`; они не возникают от обычного чтения, иных техник или OOC. Стадии и разрешённые эффекты берутся из `campaigns/shiki/contract/PROGRESSION_RULES.json`. Старый `PACT_BURDEN_LIVE.json` — материализованный снимок на прошлое время: его поле `last_at` **не означает время самой свежей сцены**, если не было события техники. Пакт не теряет ни балла при многократных коротких переходах времени. В FAST_SCENE обновляется только вычисленная проекция.

## Восстановление и межсессионный переход

Перед закрытием сессии собрать текстовые ходы в порядке `s03.text.064`, `065`, ... из неизменяемых файлов, сопоставить их с базовым чекпоинтом, с исходным журналом и пользовательской историей, применить согласованные события в SQLite через движок. Выполнить `verify --full` и сверить SHA. **Не принимать одни сокращённые summary за первичный текст** и не утверждать задним числом, что старые незаархивированные ходы имели точный оригинал там, где он недоступен.

Избыточный пересказ при сцене не заменяет сохранения: быстрый пакет — индекс ближайшего действия, полные ходы — источник, SQLite — принимаемая база после проверенного воспроизведения. Никакой специальный быстрый режим не разрешает терять факты, подменять знания NPC, придумывать скрытый сюжет, навязывать действия Шики либо нарушать стабильные броски.
