# NPR — быстрое сохранение сыгранного

Источники подхода: `sifiroth-gif/Bleach-RPG-/docs/GITHUB_CHAT_CHECKPOINTS.md` и реализованные в `NPR` `Campaign.prepare/confirm`, `verify`, `checkpoint`. Это **адаптация протокола**, не копия несовместимых файлов: Bleach использует журналы, контуры и JSON runtime, NPR — SQLite и `state.json`.

## Режимы

| Команда | Когда | Результат | Что не делает |
|---|---|---|---|
| `append` | После уже сыгранной связной сцены либо серии действий | За один вызов подтверждает ранее показанный pending (по точному тексту и receipt), последовательно записывает уже сыгранные реплики, действия, события, факты и часы NPC в SQLite | Не перегенерирует карточки 55 NPC, не делает bootstrap, не утверждает, что восстановленное краткое описание — дословная сцена |
| `handoff` | При смене чата/сеанса | Маленький `handoff.json`: текущие координаты, последние 3 подтверждённых хода, pending и ближайший мировой процесс | Не подтверждает ожидающий ответ, не меняет SQLite |
| `checkpoint` | После значимого необратимого события, большого перехода времени или перед сменой сессии | Прочитанный и проверенный согласованный снимок SQLite + `state.json` | Не запускает `init`, не изменяет мир, не переписывает историю |

**Нет фиксированного числа реплик между сохранениями.** Следует сохранять после причинно важного узла и перед потенциально дорогим переходом, а не запускать весь цикл CI после любого предложения игрока. Обычная игровая реплика должна писаться сразу. Важные сцены ведутся в чате; их периодическая реконструкция обязана сохранять исходный ввод игрока и помечать краткий текст как реконструированный.

## Протокол работы

1. Прочесть один раз актуальную `state.json` из `game-state/shiki`, проверить совпадение SHA256 с SQLite через `verify`. Игровые ветки `main` и `game-state/shiki` не смешивать.
2. Входной запрос `NPR-QUICK-SAVE/1`: `mode`, `campaign_id`, `instance`, `expected_revision`, `source_ref`; для `append` — `turns`, при существующем pending — `observed_pending` с `turn_id`, `draft_sha` и **точным `observed_text`**. Только текст ответа, действительно показанный в чате, может быть подтверждён.
3. Запустить `python -m rpg_engine.quick_save STATE_DIR REQUEST_JSON NEW_OUTPUT_DIR`. Обработка идёт на **копии**: проверка исходного манифеста, отдельная сверка опубликованного pending, подготовка и подтверждение сыгранных событий в хронологическом порядке, readback, `verify`, SQLite backup и новый `state.json`.
4. Публикация в приватную ветку **одним** Git commit двух файлов `campaign.sqlite` и `state.json`, после проверки ожидаемого HEAD. При конфликте Git push не форсировать; сперва восстановить новый HEAD. Сразу проверить SHA и байты вновь опубликованных файлов. Не говорить «сохранено», пока проверка не прошла.
5. При сбое ничего не перезаписывать. Незавершённый pending восстанавливать по draft, не подтверждать автоматически. Повторную запись проверять по стабильным ID ходов и ревизии. Не копировать чужие SQLite-базы и не начинать новую кампанию поверх имеющейся.

### Что именно хранится

- Точный исходный запрос игрока; время и место; метка источника (чат, сеанс), отдельные события и последствия NPC; подтверждённые факты и остающиеся гипотезы.
- Для ретроспективной загрузки — префикс `[Восстановление из сыгранного диалога]` в поле ответа вместо ложного утверждения о дословной записи.
- Для нового ответа ведущего — прежний двухфазный путь `prepare` перед публикацией и `confirm` после того, как текст виден. Независимого сигнала доставки от ChatGPT у GitHub нет.

### Технические пределы

Проверка SQLite + резервное копирование маленькой базы NPR дешёвы. Основная задержка связана с сетью и очередью GitHub Actions, поэтому **сокращать число запусков**, а не жертвовать журналом или проверкой целостности. Служебный процесс не должен выдавать игровые сцены вместо ведущего.
